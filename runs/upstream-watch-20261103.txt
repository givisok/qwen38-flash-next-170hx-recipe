## 1. TOP FINDING: our prod loses prefix-cache DEPTH on replays (bug live here)

Upstream PR vllm-project/vllm#52244 "[Bugfix][V1] Restore hybrid GDN
prefix-cache hits under MTP spec decoding" (open, upd 2026-11-03) describes
exactly our stack class: hybrid GDN target + MTP drafter. On Qwen3.5-122B they
measure replays that never reach the possible hit depth, and prompts whose
length is a multiple of the hash unit get NO hit at all. Root cause: lookup
caps at prompt_len-1, the MTP/EAGLE drafter rewinds one more hash unit, but
the producer publishes the GDN state at the prompt's own tail boundary
(prompt_len // unit * unit) which is at/above the cap -> the recurrent state
cannot resume at the hit point.

Our probe on prod (MTP-4 @0.95, thinking off, temp 0, bodies = RU filler +
unique header per tag; block-hash chains make cross-tag hits implausible):

tag  prompt   1st send   REPLAY cached   depth
A     4773        0          2368         50%
B     5152     1728          4752         92%
C     7115        0          5184         73%
D     8230        0          5184         63%   <- hard cap, same value as C

- C and D BOTH stop at exactly 5184 = 3x1728 = 6x864 (our GDN page is 1728,
  MIXED_PREFILL_CHUNK is 864) -> a systematic ceiling, not noise.
- A (below the ceiling) still loses half its depth.
- /metrics prefix_cache_hits_total deltas match usage numbers exactly.

Cost in real traffic: every same-context turn (the agent pattern: history +
new tail) re-prefills 8-50% of an already-cached context. On a 25k-token
neighbor context that is 2-12k tokens of avoidable prefill -> feeds the
"prefill-storm neighbor" decode collapse documented in storm-ab-20261102.txt.
So fixing depth also softens the storm for same-session agents.

Candidate job (needs user word): read the fork's prefix-cache handles
(g4bwy prefix-cache + LPT2048; the 5184=3-page cap may be a fork knob, not
the upstream bug), port the #52244 mechanics if that is what we have, then
reboot + full battery. Not started.
